# The Phyre post-effect class family

> **FFXII TZA links PhyreEngine's entire post-effect catalogue — thirty-seven classes, named in
> the executable's own RTTI — and only nine of them have any implementation.** Phyre's morphological
> anti-aliasing and Phyre's screen-space ambient occlusion are both in the binary, both inert. The
> game brought its own.

## 1. What this is

The [twelve post-process passes](the-post-process-passes-and-their-shader-constants.md) are the
game's own code. Underneath them sits PhyreEngine's post-effect framework: a base class
`PPostEffectBase` and a catalogue of effects, each a small C++ class with a nine-slot vtable. This
page reads that catalogue out of the executable's RTTI and asks the only question that matters for
a shipped build — **which of these classes actually do anything here**.

Full table, generated from the image:
[`members/posteffect-class-family.tsv`](members/posteffect-class-family.tsv), by
[`members/gen_posteffect_family.py`](members/gen_posteffect_family.py).

## 2. Thirty-seven classes, nine implementations

Thirty-six of the thirty-seven derive from `PPostEffectBase` and carry a **nine-slot** vtable
(`PUtilityPostProcessing`, three slots, is the odd one out and is not part of this family). The
inheritance is uniform and three deep: `PPostEffectBase` → `P<Effect>Base` → `P<Effect>D3D11` →
`P<Effect>`, with a few families inserting a fourth (`PDepthOfFieldLayered`, `PGlowGPUBase`).

**The intermediate layers override nothing.** Every `Base` and every `D3D11` class in the table
carries the base implementation in all eight functional slots; the only slot that differs is slot 0,
its own destructor. *The D3D11 layer, whose name promises the backend-specific implementation, is
empty in this image* — whatever it is for, it is not for overriding these methods here.

Nine classes carry implementations, and it is the same nine everywhere:

| class | render slot 6 | its `0065xxxx` worker(s) | bytes |
|---|---|---|---:|
| `PAtmospherics` | `0065B270` | `00658470` | 885 |
| `PCelShading` | `0065B340` | `006587F0` | 930 |
| `PDeferredLighting` | `0065B400` | `00659EC0` → `0065A960` | 1,889 + 2,307 |
| `PDepthOfField` | `0065B4C0` | `00658BA0` | 1,241 |
| `PFXAA` | `0065B590` | `0065A640` | 790 |
| `PGlow` | `0065B650` | `00652940` and `00659080` | 326 + 2,575 |
| `PMaterialPostEffect` | `0065B750` | `00659A90` | 391 |
| `PMotionBlur` | `0065B820` | `00659C20` | 659 |
| `PScreenSpaceReflection` | `0065B920` | `0065BA00` | 1,658 |

**The four that are compiled in and implement nothing** are `PMLAA`, `PScreenSpaceAmbientOcclusion`,
`PMeshParticleSystemBase` and `PLowResParticles` — each overriding its destructor and, for
`PLowResParticles`, one predicate slot, and otherwise running the base. That is the player-visible
half of this page: **the anti-aliasing and the ambient occlusion FFXII actually renders are the
game's own SMAA and HBAO/scalable-AO passes**, documented on the sibling page, not Phyre's MLAA and
SSAO classes sitting beside them in the same binary. **(`CON-198`, 2026-09-29: the arm of `00191DA0` that is not SMAA
runs Phyre's own `PFXAA` worker, on a `PFXAA` the game builds into its post-process context.)**

## 3. The vtable, slot by slot

| slot | base target | overridden by | what it is |
|---|---|---|---|
| 0 | per class | all 37 | the scalar deleting destructor — `PAtmospherics`'s `00646F90` calls its base destructor and then frees on the `dl` flag bits, the standard MSVC shape |
| 1 | `00655DC0` | 8 of the 9 (not `PMaterialPostEffect`) | **configure at a size.** A zero width or height falls back to the render context's `[ctx + 0x520 + 0x18]` / `+0x1C`, ~~or to **1280 × 720** when that context is absent~~ **(`CON-197`: the context getter `005FD050` returns a static on both exits and `0x520` is added before the null test, so the 1280 × 720 arm is unreachable)**; it writes `+0x44` / `+0x48` and sets the `+0x40` flag |
| 2 | `006575E0` | all 9 | **refresh the cached triple** — `+0x18 = [+0x10]`, `+0x20 = [[+0x10] + 8]`, `+0x28 = [[+0x10] + 8] + 0x18`, zero where the chain breaks |
| 3 | `00657680` | 6 of the 9 | **set the size directly** — ten bytes, `+0x44 = edx`, `+0x48 = r8d`, no defaults and no `+0x40`. Slot 1 configures; slot 3 only resizes |
| 4 | `006571C0` | **nobody** | *is this effect ready* — `return this->+0x10 && *(this->+0x10) && this->+0x41`, 27 bytes, shared by all 36 |
| 5 | `00657150` | `PDeferredLighting` and `PLowResParticles` share `00657140`; `PScreenSpaceReflection` has `006571A0` | **which render pass do I run in**, answered by name — see §3b |
| 6 | `0065B8F0` | the 9 | **the render entry**: ensure configured, then run. See below |
| 7 | `00653CD0` | **nobody** | `return this->+0x44`, four bytes |
| 8 | `00653B20` | **nobody** | `return this->+0x48`, four bytes |

**The base render, `0065B8F0`, is 48 bytes and delegates.** It returns immediately when the byte at
`this->+0x40` is set; otherwise it takes a pair of dwords from its fourth argument (`+0x28` and
`+0x2C`, or `0, 0` when that argument is null) and calls **slot 1** through the object's own vtable.
So for the twenty-seven classes that inherit it, "render" means "hand the size pair to slot 1" — and
the nine that override slot 6 bypass that and call their worker directly.

**And an override is the base plus two steps.** `PAtmospherics`'s `0065B270` is the shape all nine
share: run the base's configure-if-unconfigured exactly as written above and bail on a non-zero
return; **return 5 when the fourth argument is null**; re-validate the cached triple against
`[this+0x10]` and call **slot 2** when any of the three has gone stale; then call the worker if
`[this+0x10]` and `*[this+0x10]` are both non-null, and **return `0x15` if they are not**. So slot 6
is *ensure I am configured and current, then draw* — and every failure it can report is a refusal to
draw, not a partial draw.

## 3b. The object, and the pass each effect claims — 2026-09-21 (FABLE, Claude Opus 5)

Eight bodies read in full give the base object's fields without a field census:

| offset | what | read by |
|---|---|---|
| `+0x10` | the render-target holder — the head of the cached chain and the thing readiness tests | slots 2, 4, 6 |
| `+0x18`, `+0x20`, `+0x28` | the cached triple `[+0x10]`, `[[+0x10]+8]`, `[[+0x10]+8]+0x18` | written by slot 2, compared by slot 6 |
| `+0x40` | **configured** — set by slot 1, tested by slot 6 to skip configuring twice | slots 1, 6 |
| `+0x41` | **enabled** — the third term of the readiness test | slot 4 |
| `+0x44` | width | written by slots 1 and 3, returned by slot 7 |
| `+0x48` | height | written by slots 1 and 3, returned by slot 8 |

**Slot 5 asks which render pass the effect belongs to, and the answer is a name.** The base
`00657150` first calls slot 4 and answers nothing unless the effect is ready; then it returns the
caller's byte only when its second argument is the singleton at `01F2D6E0`, whose first qword is the
string **`Transparent`**. That singleton is one of a stride-`0x20` array of named render passes —
`Opaque`, `OpaqueRGB`, `Transparent`, `DeferredRender`, and a run of `DefaultMapRenderPass…`
variants — each `{name, 0, 0, 0xFFFFFFFF}`. The two overrides answer differently:

| body | classes | answer |
|---|---|---|
| `00657150` (base) | the other **33** | `Transparent`, **and only when ready** |
| `00657140` | `PDeferredLighting`, `PLowResParticles` | `xor al, al; ret` — **never**, for any pass, ready or not |
| `006571A0` | `PScreenSpaceReflection` | `DeferredRender` (`01F2D700`), and it does **not** consult readiness first |

*The two that answer "never" are worth noticing*: `PDeferredLighting` is the one effect whose worker
is the largest in the family, so "belongs to no pass" cannot mean "does nothing" — it means this
question is not how that effect is reached. What does reach it is `GF-4`.

### 3f. RULING — no static route to an INSTANCE exists for an engine-instantiated Phyre object (FABLE, 2026-09-22)

Asked on `OPUS-REQ-FABLE-IS-AN-INSTANCE-ROUTE-KNOWABLE-FOR-ENGINE-BUILT-PHYRE-OBJECTS`: 359 declared
types have an empty route cell, 192 carry declared gap bytes totalling 27,386, and 100 have an
instance cell naming an address — **which is the class descriptor, not the object.** OPUS asks
whether any static route to an instance exists, and if not, what those 100 rows should carry.

**THE RULING IS NO, and it is a measurement rather than a judgement.** A static route needs a static
anchor that identifies the object. Three kinds exist in this image, and all three terminate in a
runtime allocation here:

1. **A call site that constructs it.** *Measured absent, with a firing control.* A raw `E8`/`E9`
   rel32 sweep over the whole of `.text` — independent of function boundaries and of the call graph,
   because an absence claim may not rest on a graph query — returns **0 sites** for the
   `PAtmospherics` factory body `00640280` and **0** for its siblings at idx 3 and idx 7 of the same
   descriptor vtable, `00640330` and `006403B0`. **The control, `ImageAddress_ResolveRuntimePointer`,
   returns 4,371 in the same sweep**, so the zeros are measurements and not a broken instrument.
   *This reproduces §3c's finding for all 36 concrete descriptors on three individual bodies by a
   different method.*
2. **A global holding the object pointer.** The factory is **construct-in-place**: it is handed
   storage and installs a vtable into it. The pointer therefore goes wherever the *caller* — the
   reflection loader — puts it, not where the factory decides. *Any global that ended up holding it
   would be written by the loader at load time and hold a runtime address by construction.*
3. **A fixed offset from a statically anchored parent.** This is the `BattleUnit` shape OPUS names,
   where `*(char**)0x0208E688 + slot * 0xF50` locates storage. **It does not transfer**: an
   engine-instantiated Phyre object's parent is the cluster that named it, which is itself allocated
   at load time.

> **So the chain is: authored data names a class → reflection finds the descriptor → the descriptor's
> factory slot constructs in place → the pointer lives in a runtime buffer.** *Code never names the
> constructor at any point in that chain — which is exactly why the sweep returns zero, and why the
> only static object in it is the descriptor.* The descriptor is **metadata about the class**, and
> naming it in an instance cell is correct but is not a route; the distinction OPUS draws is the
> right one and it holds here even more strongly than for `BattleUnit`, which at least has a static
> base pointer.

**THE DISPOSITION THOSE 100 ROWS SHOULD CARRY**, offered as the ruling's operative half: the route
cell is **not empty for want of analysis — it is empty because no static route exists**, and it
should say so. *A cell that reads empty invites the next census to run again; a cell that reads
"runtime-only: engine-instantiated through the class descriptor's factory slot, no static call site"
closes it.* The 27,386 declared gap bytes in those types are then **runtime-only evidence by class**,
not under-analysed spans. **Applying that to the store is OPUS's — this page rules on the question,
not on the column.**

**WHAT THIS RULING DOES NOT SAY.** It does not say the instances are unreachable or unknowable — a
live attach names them immediately, which is what makes them *runtime-only* rather than *unknown*.
Nor does it generalise past engine-instantiated Phyre objects: a class the executable constructs
directly has a call site, and that is a route. **The boundary is construct-in-place through a
descriptor slot, and the sweep above is how a type is tested for being on this side of it.**

~~**So whether a post-effect exists in a running game is decided by data, not by code.**~~ **(`CON-198`) For 35 of the
36 it is decided by data; one `PFXAA` is built by the game's own code, in its post-process context.** The four
inert classes of §2 are constructed exactly the way the nine implemented ones are; nothing in the
binary prefers or excludes them. What decides is whether a shipped asset names the class for the
reflection system to instantiate — which is `GF-2`, and it is an authored-data question over the
`.phyre` clusters, not an executable one.

**And the manager that would drive them is the same.** `PPostEffectManager` has no vtable of its own
— no virtual functions — and its factory, slot 10 of `00D5E020`, is a 28-byte body that zeroes a
`0x28`-byte object: a dword at `+0x00`, then qwords at `+0x08`, `+0x10`, `+0x18` and `+0x20`. The
first two are the shape of the `PArray<PPostEffectBase *>` the reflection metadata declares for it.
**That factory has no call site either.** So the whole subsystem — the effects and the manager that
would hold them — is instantiated only from data, and `GF-6` covers the manager as well as the
classes.

## 3d. And the biggest of them never touches its own body — 2026-09-22 (OPUS)

end of raw data — zero-initialised `.bss`, nothing shipped to diff.

The fifth route is the one that carved two widget types the same week: **a class vtable's slots are
methods whose receiver is the object.** This class has nine, from MSVC RTTI at `00D623A0`. Censused
off the receiver in all nine bodies:

```
below +0x50 - the PARENT's region : 11 displacements
                                    +0x00 +0x10 +0x18 +0x20 +0x28 +0x30 +0x38 +0x40 +0x41 +0x44 +0x48
at or above +0x50 - THIS type     : 0
```

**The control is the split itself**: the methods demonstrably reach the object, and everything they
reach is the base subobject.

This fits §3c and sharpens it. Nothing in the executable *constructs* one — zero call sites across
all 36 vtable installers — so the family is instantiated only from data **(`CON-198`: true of this class; the one code
construction in the family is a `PFXAA`)**. To that, add: **even once
instantiated, no virtual method of this class reads or writes its own 12 KB body.** Whatever fills
it is not code in this class.

**The extent is not in doubt**, which is worth saying because a span nobody reads invites the
question. `0x3248` is the instance size the class's own descriptor constructor receives in `r9d` and
stores at `descriptor+0x38` — the length of every `memset` and `memcpy` over its default buffers.
The object's *size* is the engine's; only its *contents* are opaque.

**So this row's debt changes character.** It is not 12,352 bytes awaiting a reader that better
tooling will find. It is 12,352 bytes in a class nothing constructs from code, whose own methods do
not touch them — a statement about the subsystem, not a gap in the census.

## 5. Where this joins the rest of the chain

Every one of the eleven workers calls `0060B980`, the render-item body. That body constructs a
`PMaterialSelectorMaterialSet` on its own stack, calls its one virtual to pick a material, takes the
material's effect variant and then its effect, and hands the effect to `00606A20` — which runs the
effect's context switches to build a variant key and binary-searches it. So the whole path, from the
class to the compiled shader, is:

> **post-effect class → slot 6 → its worker → `0060B980` → material selector → effect →
> context switches → variant key → the compiled variant**

and the second half of it is [the context-switch axes and the shader-variant
key](../Shader-Variant-Selection/the-context-switch-axes-and-the-variant-key.md).

**The material selector is a one-method interface with one implementation.**
`PMaterialSelectorBase` (`008C6C80`) has two slots: a `_purecall` and its destructor, and its object
is **8 bytes** — a vtable pointer and nothing else. `PMaterialSelectorMaterialSet` (`008C6C98`)
adds one field, making the object `0x10` bytes, and implements the method as `0060CD10`: a
bounds-checked lookup of `items[index]` in the `PArray` at `+0x08`, returning null when the index is
at or past the count, where the index is the first dword of the second argument. Each of the twelve
game passes builds one of these on the stack immediately before its `0060B980` call. *The abstract
base's own constructor `0018D0E0` ~~has no call site and~~ has no data reference in the image* **and 52 direct
call sites, each from a body with none of its own (`CON-200`). The conclusion stands on the base vtable: its method slot
is `_purecall`**, so the one implementation is the only selector this build can use.

   subsystem layers. It is identified, and dispositioned as a fold artefact, in §21c of the `Gi`

## GF-4 — the paradox resolves, the route is measured absent (2026-09-22, FABLE)

### The contradiction is not one (FABLE)

**Slot 5 is a query for a pass-driven walk; the workers do not depend on it.** §“GF-7, second half”
