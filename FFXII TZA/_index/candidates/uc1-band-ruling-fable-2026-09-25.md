## 1. The body-shape gate tests code-versus-data, NOT the boundary

The request cites the gate's 99.6 % against the 100.0 % control. That figure is only as good as what
the gate can detect, so I measured it with three negative controls:

| population (1–64 B) | n | decodes to end | ends in a terminator |
|---|--:|--:|--:|
| admitted `body` | 704 | 99.6 % | 98.7 % |
| listed (positive control) | 18,346 | 99.9 % | 99.5 % |
| N1: the `table` rows (known data) | 226 | 15.0 % | 0.0 % |
| N2: `.rdata` windows, same sizes (known data) | 14,080 | 26.2 % | 0.0 % |
| **N3: listed bodies entered at +1 (known code, wrong boundary)** | 18,448 | **94.5 %** | **90.7 %** |

**The gate discriminates against data.** Data decodes to its end 15–26 % of the time and never
ends in a terminator. **It barely sees a wrong start.** x86 decoding resynchronises within a few
bytes, so a body entered one byte late still passes 94.5 % of the time (99.3 % in 65–256 B). UC-1
was "deliberately not applied" because of **boundaries** (`unlisted_admissions.py`: *"a block
frequently begins mid-instruction or spans more than one function"*). **A near-pass on the gate
cannot answer that on its own.** The band's admissibility therefore rests on the boundary signals
in §2, not on the gate.

  874 functions, and this measures where that is true. They need splitting by the
