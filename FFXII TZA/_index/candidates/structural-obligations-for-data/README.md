## 6. DATA's counting decision (SWE2-DATA, 2026-09-28)

Each class is counted by exactly one instrument; nothing is double-counted into the register and
nothing is dropped.

1. **Page-only boxes (49): counted, not registered.** They are page-local residue — work-items the
   page owner left open — not standalone questions, so they get no register ids (registering 49
   vague rows would flood the ledger with non-questions). The counting instrument is
   `check_questions.read_boxes`; the figure is now *durable*: `progress_report.parse_page_boxes`
   reports `page_boxes.no_id` (split `no_id_untracked` for uncommitted pages) in the route's
   snapshot, fingerprint-bound like every other counter — the count drifts the route when a peer
   edits a box. Renders as "page-box obligations" in `snapshot.md`'s input table.
   - **Consistency rule:** an unticked structural box is a residue of the page's *owning system*.
     Where a system verdict reads MET while its page still carries unticked structural boxes
     (e.g. S-04 vs. the encoded-id contract's §14 "tagged output slots" / "caller reentrancy"
     boxes), the conflict is flagged to the verdict's owner — the box does not auto-unmet a
     verdict, and a MET does not silently close a box.
   - **Process boxes** ("obtain independent acceptance") are NOT A QUESTION under the class-2
     rule; their carrier is the board review queue (§5). They stay unticked while the review is
     pending — that is honest — but they are not knowledge debt and need no register row.
2. **Withdrawn-row boxes (29): dispositioned.** A closed row's unticked box misreports pending
   work, so all 29 were ticked with a carrier note (`closed — the register row is <status>.`),
   matching the corpus convention `check_questions` documents ("all ticked boxes whose ids the
   register already records as closed"). Post-pass the instrument reads `closed_id = 0` and the
   new counter detects any regression. Verified: `check_questions` still reports
   *questions consistent* (1461 boxes, 0 cross-check drift).
3. **Register rows (11):** no change — they are the gate's denominator already; holders per §3.
4. **DISCOVERED type-store fields (1,497): counted where they live.** `TYPE-COVERAGE.md`
   (`types_index.py --coverage`) is the correct instrument — the field-resolution ladder
   (DISCOVERED → TYPE RESOLVED → SEMANTICALLY IDENTIFIED → …) is a coverage dimension, not a
   questions dimension; folding it into the register would conflate "field not yet typed" with
   "open question". A gate-level floor on this frontier is a `goal_gate` feature for FRONTIER,
   not a DATA register action.
5. **Pending reviews (16):** informational — `TEAM.json` is the instrument; no ledger change.

Net gate effect: the questions dimension's denominator (register rows) is unchanged — correct,
since no class above is a register question — but the previously *invisible* residue is now
visible in the route report: 49 page-local obligations, 0 closed-row, 5 live-row unticked boxes.
