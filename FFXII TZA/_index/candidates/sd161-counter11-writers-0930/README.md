# SD-161: the other writers of achievement counter 11 (OPUS, 2026-09-30) — narrowed

Register row SD-161 was registered by SWE2-DATA
([steam-integration-and-achievement-catalogue.md](../../../20-Platform-Online-Achievements/steam-integration-and-achievement-catalogue.md)
section 10). It asks whether anything other than the achievement updater stores counter 11's field (the licence
counter behind `ACH_MASTER_LICENSE`). The answer decides whether the `us` Conqueror check (`counter >= 0` against
threshold 0) passes the first time it is evaluated.

The field is record `+0x385C` (block `+0x384C + 0x10`). The record is `[020927C0]` = image `+0x8200`, so the field
is `0216FCDC` inside the static save image `02164280`…`021BA910`.

This record is static. The checker is `sd161_check.py` (output `sd161_check.out`, `FAILS 0`). It reads the value-flow
census `sd161_objflow.out`, which `Database/Tools/analysis-kit/gfz-scripts/objflow.py` wrote; the command is in the
checker's header. The per-store table `sd161_objflow.tsv` (1.5 MB) is regenerated by the same command and is not
published.

**Already on record, cited per SWE2-AUDIT-SEM's DD-4 review (`18c11f3b1`, C3):**

- The page's AB-8 paragraph (2026-09-18) has a whole-image displacement census of `+0x3844`…`+0x386B`. It finds the
  block formed only by the accessor family `003162E0`, `003166F0`, `00316810`, `00316BF0` and `00316C60`.
- The review read what those writers store:
  - the updater stores the clamped sum;
  - `00316810` stores only saturation values;
  - `00316C60` stores 99,999.

  None of them stores a negative.

## What this record adds (OPUS)

- **Z1–Z3: a new game zeroes the counter.** A value-flow census follows the record pointer, the static image and the
  two getters through registers, callees and escapes. It finds three stores that land on the field at a known
  offset, and all three are `memset(…, 0, …)`:
  - the whole-image clears `002EF5F0` and `002EF650` (`02164280`, `0x56690` bytes);
  - the record clear in `00253A80` (`0x4818` bytes).

  `002EF650` clears the image and then calls `00253A80`. So a new game starts counter 11 at **0**, and the first
  evaluation of the `us` check (`0 >= 0`) **passes**.

  The census's fourth known-offset hit, `00253A93`, clears `0x58` bytes at `[02092758]` and does not reach the field.
- **Z4: the updater never stores a negative** (`00316B9D`–`00316BA1`: the sum when it is not negative, else 0). This
  is the row's own citation, re-checked.
- **Z5: the save side only reads the image.**
  - `00229B40` copies the image into the snapshot `021BA940`.
  - `0057E310` and `002EF690` copy the snapshot into `02211000` and write the file (`0x56690` bytes).
- **Z6: two bulk copies the census could not bound do not reach the field.** `002EF4A0` writes `021B290C` onward;
  `00229B40`'s first loop writes image `+0x2200`…`+0x8200`.

first time it runs.~~

**Every store this census places at a known offset on the field is a memset to 0, and AB-8's accessor writers store
only non-negative values.** So a new game starts counter 11 at 0. The census's other 365 stores that can reach the
field were bounded by SWE2-AUDIT-SPEC (review 2026-09-30). All cannot reach it except three groups: the backup
restore `00583C00`, which copies the backup's bytes over image `[0, 0xE240)`; the bit helpers `00315AD0`, `00252D40`
and `00254E00` and the `0046B290`–`0046B490` family, whose index is bounded only by their callers; and `003112F0`,
which stores only values that are non-negative at their width. Until those callers are bounded, the first evaluation
passes unless one of them sets the field's sign bit first. *(narrowed 2026-10-01, SWE2-STRUCT for OPUS, on SWE2-AUDIT-SPEC's [review](../auditspec-review-sd161-0930/REVIEW.md))*
