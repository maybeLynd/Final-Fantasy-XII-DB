**Verdict:** apart from choosing the path, `+0x1F1` bit 3 changes two things. (1) Both bit-3-set paths (`00437130` and `00444340`) drop any primitive that has a corner whose first vertex qword is zero; the bit-clear paths always emit it. (2) For meshes only, the bit-clear inline path can scale the pass pair `param+0x50+8p` by 1/1.15 and ×1.15, and `00437130` never does. Every other input, kernel, lighting mode, UV operator, emitter and argument is the same.

# SD-199: what `+0x1F1` bit 3 changes in drawing, beyond selecting the path (cloud draft, FABLE question lane, 2026-10-03)

Source: the four listings in `cloud-input/questions/sd199/` (`004355D0.lst`, `00437130.lst`, `004434D0.lst`,
`00444340.lst`). Addresses are VAs with the image base included. Callees are cited as "`CALLER` + 0xNN", meaning the
call instruction's offset from the calling function's entry. This is a text-only draft, so every line needs FABLE's
re-read against the executable.

- `param` is the draw-parameter block (`r15` in `004355D0`, `r13` in `00437130`, `r14` in `004434D0`, `rdi` in

- `nXX` is the record's word at `+0xXX`.
- `I` is the inline path of `004355D0`, and `F` is `00437130`.

### A.2 The differences

**A-1: `F` skips any primitive that has a corner whose first vertex qword is zero. DRAWN, conditional (see "needs
local check" 3).**
- **What `F` does.** In every one of its 12 emit loops, `F` copies the 16-byte vertex-table entries
  (`r14 + 16·index`) of the primitive's corners to `[rbp+0x60]`, `[rbp+0x70]`, `[rbp+0x80]` and, for quads,
  `[rbp+0x90]`. It then compares each one's first qword with 0, and any zero jumps past the emitter calls to the
  counter block. Where the skip happens:
  - value 5: `00437894`–`004378BF` (tri, `[02AEE900]` set), `0043796C`–`00437999` (quad), `00437A1E`–`00437A41`
    (tri, clear), `00437AEC`–`00437B19` (quad);
  - value 1: `00437BE8`–`00437C13`, `00437D79`–`00437DB2`, `00437F18`–`00437F43`, `004380A9`–`004380E2`;
  - other: `0043824F`–`0043827A`, `004383CC`–`00438405`, `0043854C`–`00438577`, `004386C0`–`004386F9`.
- **What `I` does.** `I` performs the same copies and calls the emitters unconditionally. The `I` call sites that
  correspond to the skipped calls are:
  - `0039E820` at `004355D0`+0x87B, `0039EC30` at +0x93B, `0039E6B0` at +0x9DB, `0039EA70` at +0xA9B;
  - `0039B840` / `0039F4B0` at +0xBCD / +0xC12, `0039B860` / `0039F9F0` at +0xD93 / +0xDD6, `0039B840` /
    `0039F2B0` at +0xEDC / +0xF21, `0039B860` / `0039F780` at +0x10A3 / +0x10E6;
  - `0039B840` / `0039F4B0` at +0x1210 / +0x123C, `0039B860` / `0039F9F0` at +0x139B / +0x13C7, `0039B840` /
    `0039F2B0` at +0x14CE / +0x14FA, `0039B860` / `0039F780` at +0x165B / +0x1687.
- **The skippable calls in `F`.** They are:
  - `0039E820` at `00437130`+0x79C, `0039EC30` at +0x876, `0039E6B0` at +0x91E, `0039EA70` at +0x9F6;
  - `0039B840` / `0039F4B0` at +0xB61 / +0xB99, `0039B860` / `0039F9F0` at +0xD1F / +0xD57, `0039B840` /
    `0039F2B0` at +0xE91 / +0xEC9, `0039B860` / `0039F780` at +0x104F / +0x1087;
  - `0039B840` / `0039F4B0` at +0x11CA / +0x11F3, `0039B860` / `0039F9F0` at +0x1374 / +0x139D, `0039B840` /
    `0039F2B0` at +0x14C7 / +0x14F0, `0039B860` / `0039F780` at +0x1668 / +0x1691.
- **What is tested.** The tested qword is bytes 0–7 of the entry. It is zero only when all 8 bytes are zero (a
  bit-pattern test, not a float compare).
- **What a skip changes.** A skipped primitive emits nothing in `F`, but the same primitive is emitted in `I`. Vertex
  counts, packing and the arguments of an emitted primitive are otherwise identical. The skip does not shift any
  stream:
  - the position, colour and UV counters advance on the skip path;
  - the value-1 per-primitive byte is consumed before the test.
- **Why it counts as DRAWN.** It is DRAWN whenever some entry has a zero first qword: a primitive appears under
  bit 3 clear and is missing under bit 3 set. If no such entry ever reaches a draw, or the bit-clear emitters reject
  it themselves, the difference shows nothing; the listings cannot settle that.

**A-2: `I` can scale the pass pair `param+0x50+8p` by (1/1.15, ×1.15); `F` never does. DRAWN, provisional (see
"needs local check" 1–2).**
- **Where `I` does it.** `I` does it in both arms reached when `param+0x1F2` bit 0 is clear:
  - **`+0x1F2` bit 1 set** (after the `0043E840` call at `004355D0`+0x73C or +0x74E). `00435D23`: if
    `param[0x130+p] == 4`, `I` calls `0053DD10` at `004355D0`+0x75E. If that returns 1 (`00435D33`):
    - `[r12]` becomes `[r12] / 1.15` (`divss` `00435D45`);
    - `[r12+4]` becomes `[r12+4] × 1.15` (`mulss` `00435D49`);
    - the stores are at `00435D4D`/`00435D53`.

    Both lanes then get the same +0.5 as in `F` (`00435D5A`–`00435D6B`, stored at `00435D9B`/`00435DA2`).
  - **Neither `+0x1F2` bit** (`00435D71`): the same test on `param[0x130+p] == 4` is followed by `0053DD10` at
    `004355D0`+0x7AC. If that returns 1, the same divide and multiply follow (`00435D93`/`00435D97`), stored at
    `00435D9B`/`00435DA2`.
- **What `F` does in the same arms.** `F` goes straight to the +0.5 in the bit-1 arm (`004377F2`–`0043780C`). With
  neither bit it does nothing at all (`004377B2`). `F` never calls `0053DD10` and never loads 1.15.
- **Where the pair goes next.** The pair is the `r9` argument of the builders `0039B840` / `0039B860`. The value-4
  case falls to the "other" emit branch, so the modified pair reaches those builders in exactly the case it is
  modified:
  - `I`: `004355D0`+0x1210, +0x139B, +0x14CE, +0x165B, with `r9 = r12`;
  - `F`: `00437130`+0x11CA, +0x1374, +0x14C7, +0x1668, with `r9 = [rsp+0x58]`.
- **Side effect.** The pair is written back into the parameter block in place (`[r12]` is `param+0x50+8p`), so it
  persists past this call.
- **Why it is provisional.** It is DRAWN if the builders turn `r9` into emitted UV or STQ data, and if
  `0053DD10` returns 1 at run time. Neither callee is in the listings.

**Everything else is BOOKKEEPING:** register and stack-slot allocation, frame size, the separate versus shared
epilogue, and when the per-position floats are loaded (`F` loads them only after a primitive passes the test). None
of these changes a value that reaches an emitter.

`02AEE900`/`908`, `02AEEA20`–`02AEEA50`, `02AEEAA0`, `02AEEBF0`–`02AEEC20`) and the same constants.

### B.2 The differences

**B-1: `G1` skips any grid quad that has a corner whose first vertex qword is zero. DRAWN, conditional (see "needs
local check" 3).**
- **The test.** After copying the four 16-byte corner entries, `G1` tests the first qword of each one: corner 0 from
  `xmm2` through `movq rax, xmm2` / `test rax, rax`, the others with `cmp qword ptr [...], 0`. Any zero jumps past
  the emitter calls to the counter block. Where:
  - value 5: `00444BCB`–`00444BED` (set) and `00444CEB`–`00444D0D` (clear);
  - other values: `00444E40`–`00444E6E` (set) and `00445090`–`004450BE` (clear).
- **`G0` has no such test.** It loads the same corners (`00443CB0`–`00443CF4`, `00443DB0`–`00443DF4`,
  `00443F00`–`00443F54`, `00444110`–`00444164`) and always calls `0039EC30` (`004434D0`+0x84D), `0039EA70` (+0x94D),
  `0039B860` / `0039F9F0` (+0xB19 / +0xB3B), and `0039B860` / `0039F780` (+0xD29 / +0xD4B).
- **The skippable calls in `G1`.** They are `00444340`+0x8D4, +0x9F4, +0xBF1 / +0xC1B and +0xE41 / +0xE6B.
- **What a skip changes.** A skipped quad emits nothing in `G1`, but the same quad is emitted in `G0`. Otherwise
  the vertex count (4 per quad), the packing and every argument are the same.
- **What the tested bytes hold.** The first 4 bytes of a grid entry are the two u16 fields that the mode-2 loop reads
  as the screen-position term's X and Y (`00443A21`/`00443A37`, `004448E0`/`004448F6`). So the tested qword is X, Y
  and the 4 bytes after them, all zero.

**Everything else is BOOKKEEPING:** register allocation (`G1` caches `[02AEEDA4]`, `[02AEEDAC]` and `[02AEEDB0]` in
registers and reloads them after every call, while `G0` re-reads memory), the stack offsets of the corner and UV
staging areas (`[rbp+0x50]` / `[rbp+0x30]` in `G0` against `[rbp+0x30]` / `[rbp+0x70]` in `G1`), and the pushed
registers.

## Answer to SD-199

The bit's main effect is the path it picks. Beyond that, `+0x1F1` bit 3 changes very little in how a kind-`0x54`
mesh is drawn.
- **What stays the same.** `00437130` and the inline path of `004355D0` (`00435699`–`00436CFB`) read the same record
  and parameter-block fields and the same globals. They run the same colour kernels (`00432300`, `00432CC0`), the same
  per-pass lighting switch and matrices, the same UV operators (`0043E7B0` / `00434630` / `00434760` / `0043E840`) and
  the same emit branches. They hand the same arguments to the same emitters, with the same vertex counts and counter
  strides.
- **First difference (A-1).** With bit 3 set, `00437130` silently drops every triangle or quad that has a corner
  whose 16-byte vertex-table entry starts with a zero qword. The inline path draws it.
- **Second difference (A-2).** With bit 3 clear, the inline path can rescale the pass pair at `param+0x50+8p` by
  1/1.15 on lane 0 and ×1.15 on lane 1, writing the result back into the parameter block. This happens when the
  pass's `+0x130` byte is 4, `+0x1F2` bit 0 is clear, and `0053DD10` returns 1. The pair then reaches the
  `0039B840`/`0039B860` builders.
- **The grid draws.** These are not kind-`0x54` draws, but the same bit selects between them. `00444340` and
  `004434D0` differ only in the same zero-qword skip (B-1).

So the bit's one cross-cutting drawing effect is the zero-corner skip. The 1.15 rescale applies to the mesh's
bit-clear path only. Whether either ever changes a pixel depends on two run-time facts the listings cannot settle:
- whether zero-qword entries ever reach these loops;
- what `0053DD10` returns and what the builders do with `r9`.

## Needs local check

1. **`0053DD10`.** What it returns and when (called at `004355D0`+0x75E and +0x7AC with no argument registers set
   in the listing), and whether it has side effects. The 1.15 rescale (A-2) happens only when it returns 1.
2. **`0039B840` / `0039B860` use of `r9`.** Whether they turn the pass pair (`r9 = param+0x50+8p`) into emitted UV
   or STQ data, which would make A-2 change the image. Also whether `00449AB0` rewrites `param+0x50+8p` every frame.
   If it does not, the in-place ÷1.15 / ×1.15 (and the +0.5 of the `+0x1F2` bit-1 arm, common to both paths) would
   accumulate across frames.
3. **Zero first qwords.**
   - Which producer can write an entry whose first qword is zero, into either the mesh vertex table
     (`[02AEED50]+32·n16`, indexed through `+0x170`) or the grid `[02AEED58]`. The listings do not show the producers.
   - Whether shipped draws ever produce one.
   - Whether the bit-clear emitters (`0039E820`, `0039EC30`, `0039E6B0`, `0039EA70`, `0039B840`/`0039B860` with
     `0039F2B0`/`0039F4B0`/`0039F780`/`0039F9F0`) already reject such a corner themselves. If they do, A-1 and B-1
     change nothing on screen.
4. **Population.** Whether any element that takes the inline path has a pass with `+0x130` byte equal to 4 and
   `+0x1F2` bit 0 clear. That is the only case where A-2 can occur.
