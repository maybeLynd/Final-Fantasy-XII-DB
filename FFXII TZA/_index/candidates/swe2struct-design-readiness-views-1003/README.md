## 2. The package unit (SWE2-STRUCT)

A **reconstruction package** in this view is one registered system (`S-xx` in `important-subsystems.tsv`). That is
the unit L2 is scored on and the unit addendum §4's dependency graph would use for its nodes.

Two other units exist, and the view does not confuse them with this one:
- The completion packages (`_index/completion-packages/PKG-*`) are database-completion work packages, with the stage
  vocabulary in their README §2. They can be shown as a drill-down where one names a system, but their stage is not
  this view's column.
- Category folders are an inventory axis. The systems view already shows them.

## 3. Per-package readiness view: columns and their feeds (SWE2-STRUCT)

One row per system. Each column states **one axis** (DASHBOARD-MEANINGS §1) and is never summed with another. A column
whose feed is absent is `UNMEASURED`; a failed feed is `FAILED`. Neither is ever shown as zero or green.

## 4. Integration readiness is a property of edges (SWE2-STRUCT)

Per-package readiness asks whether one system's own specification is complete. Integration readiness asks whether
two systems' contracts agree **where they meet**. It is therefore computed per **edge**, never per node, and never
averaged:

- **Edges** come from three places: a contract's `implements:` front matter when it names another system's page; its §6
  Relationships links into another category; and its "Crossings into other layers" section. A page is mapped to its
  system through `important-subsystems.tsv`. No edge is invented from folder order (addendum §4).
- **Edge state** shows, side by side: both endpoints' per-package columns D, G and I; whether the crossing is accounted
  (the pass-22 crossings gate `audit_crossrefs.py`, and `xlayer.py` edge tokens); and the parity INTEGRATION dimension
  of any pilot on either side. The weakest of these is the edge's binding gap.
- **What integration readiness is not:** both endpoints being scoped L2 MET. A11 applies here too, and the binding
  gap names the edge.

## 5. Maturity labels: §6's vocabulary, no new scale (SWE2-STRUCT)

- The view **displays** the label from the lifecycle contract's `maturity_ladder` (SPECIFICATION READY →
  ... → WHOLE-GAME INTEGRATED). FABLE's DASHBOARD-MEANINGS §6 owns each label's criteria. This note defines none.
- **Phase gate:** while `current_primary_phase` is `DATABASE`, the highest label any package can show is SPECIFICATION
  READY. Anything beyond requires primary reconstruction, which needs user authorization
  (`automatic_transition_from_database_ready: false`).
- A DB-phase parity pilot (column F) is a bounded probe. Per addendum §13, a running differential harness is not a
  native replacement, not an integrated subsystem and not parity certification.
- **Proposed evidence for SPECIFICATION READY**, for FABLE to accept or replace in §6:
  - L2 MET for the system;
  - column G has no OPEN, PARTIAL or BLOCKED row;
  - column H is all resolved;
  - column I has nothing pending;
  - column J's unresolved items are each registered.
  If §6 says otherwise, §6 wins and the view follows it.
- **Transition banner (§12):** one line above the table from `current_primary_phase` and goal_gate:
  `DATABASE IN PROGRESS — DB_GOAL NOT_MET (<goal_gate remaining>)`. It changes only when the lifecycle file changes,
  and the view never writes it.

## 6. Generated output and dashboard hook (SWE2-STRUCT)

- **Adapter:** `v_readiness` in `build_views.py` emits `view-readiness.json` per VIEW-SCHEMA.
  - `measures`: per-axis counts with numerator/denominator, scope, instrument, as_of and limits.
  - `rows`: one row per system; `tree` holds the systems and their edges.
  - `links`: the pages, contracts, census files and candidate records themselves (A17 drill-down).
- **Reads the generation snapshot only.** `subsystems`, `l2`, `fields`, `register`, `contradictions`, the board and
  `goal_gate` are already declared inputs. New declared inputs:
  - `types.tsv`;
  - a contract index, so `build_views` never globs live files: the census map and the six section extractions, run once
    before `begin()` like `goal_gate`;
  - `PARITY-STATUS.md`;
  - the readiness-batch EDITS lists.
- **Fills `v_systems`' "open obligations under this system"** from column G, which is UNMEASURED today.
- **Ownership:** the view is not a required view, so an absent view shows UNMEASURED. Owners follow the M3 split in
  `IMPLEMENTATION-MAP.md`: DATA writes the adapter, FABLE owns the meanings, and SWE2-STRUCT supplies columns B-D (the
  type store and census logic).
- **Priority:** P2. Nothing in it is a gate input.

## 7. Checks (SWE2-STRUCT)

New cases in `test_build_views.py`, each on a fixture generation:
1. The S-20 worked example (section 9) reproduces exactly from fixture inputs.
2. Every node `state` is in DASHBOARD-MEANINGS §1/§2/§6 or `FAILED`/`STALE`, and the server's MALFORMED check passes.
3. A missing or failed input yields UNMEASURED or FAILED, never 0 (A06).
4. With `current_primary_phase = DATABASE`, a label above SPECIFICATION READY is MALFORMED.
5. With goal_gate NOT_MET, no row, edge or banner reads complete, even when all 52 systems are scoped L2 MET (A11).
6. Census row counts match the `check_census_widths` map, and the register count matches `check_questions` for the
   same ids (no double counting, A10).
7. Edge extraction never emits an edge without a cited link or `implements:` line.

## 8. Non-goals (SWE2-STRUCT)

- No new completion metric, score, percentage or "readiness %". Columns are counts on separate axes.
- No change to goal_gate, My Progress, the terminal rule or `DB_GOAL`. L3 stays out of the database goal.
- No automatic phase transition and no maturity label beyond what §6 defines and the phase allows.
- No new board, dashboard, scheduler or acceptance database: one adapter in the existing builder.
- No apportioning of whole-database totals (F, DD) to systems by guess.
- Nothing here delays DB completion work.

## 11. Amendment, 2026-10-03: FABLE's ruling on this note (SWE2-STRUCT)

FABLE ruled on this note (`78fec6629`): **ACCEPT, with one refinement.** It was relayed by the coordinator on
2026-10-03, and FABLE amends DASHBOARD-MEANINGS §6.4 in its follow-up publish. Recorded here as the note's amendment,
superseding section 5 where they differ:

- **SPECIFICATION READY evidence: accepted as proposed in section 5, plus one condition.** The system has no PARTIAL or
  REOPENED production page that `check_status_residue.py` (FABLE, `f3b0b29d4`) classes **UNMAPPED** (a status line
  whose residue no live register row owns, and which names no process item).
- **Phase cap: ruled.** SPECIFICATION READY is the one maturity label a view may show while `current_primary_phase` is
  `DATABASE`. Every later label (SEMANTIC CORE IMPLEMENTED and beyond) may appear **only as a database-phase PROBE**,
  until the user authorizes reconstruction. Column F already carries the probes; the cap lives in §6.4, not in the
  view, and the view enforces it.
- **Page-to-system attribution for the new condition.** `system:` front matter holds a page title, not an S-id. A
  residue page therefore counts against a system when `important-subsystems.tsv` lists it among that system's pages or
  contracts. Residue pages no system lists are shown in a separate UNATTRIBUTED row, never dropped and never guessed
  onto a system.
- **Build:** the generator `readiness_view.py` writes the per-system TSV as a dashboard-generation input. Its tests
  cover the phase cap and the UNMAPPED condition. The dashboard hook is coordinated with SWE2-FRONTIER through files,
  not by editing FRONTIER's or DATA's dashboard code.
