# Visual tuning parameters — and the shipped name oracle for them

**The game ships the engine's own parameter names in plain text.** `jsondata/maps/*.json` is 459
files of per-area rendering settings, one per map, with **175 distinct named keys**:

```json
{ "mDofFocusDistance": 2.358, "mGlareLuminance": 2, "mShadowValueLerpMinForMap": 0.65,
  "mContrastR": 0.57, "m_fBlurBetweenCascadesAmount": 0.1, "m_iPCFBlurSizeForMap": 7 }
```

Corpus: `Tools/work/formats/jsondata-parameter-names.tsv`, generated by
`census_jsondata_names.py`. `jsondata/cutscenes` adds 337 more files keyed `Cut 1`…`Cut N` — the
same vocabulary applied to individual camera cuts.

## How to use it, and the line not to cross

**137 of the 175 keys are literal strings in the shipping binary**, with their VAs in the TSV. Those
are **tier 2** — a string tied to a body — and each is one xref from the function that reads it.
**That is the intended workflow: key → string VA → xref → reader → the struct field it lands in.**

> **The other 38 are tier 9 and may not name anything.** [The evidence standard](../../_index/EVIDENCE-STANDARD.md)
> sets the rule: an authored name proves what the authoring tool called a value, never what the
> binary does with it. Plain text is unusually persuasive precisely because it reads like source —
> which is exactly why the cap exists.

## What the absent half turned out to be

**27 of the 38 carry authoring-tool markers** — `mCascadeNumberCheckBoxCheckState`,
`mCascadePartition0LockCheckBoxCheckState`, `…UseStateCheckBoxCheckState`.

> **Square Enix's internal lighting-editor UI state ships inside the retail game data.** Checkbox
> states, lock states, use-state flags — the tuning tool's interface, serialised alongside the
> values it was tuning.

**The two signals agree with zero contradictions:** no tool-marked key appears in the binary, and
none of the 137 present keys is tool-marked. Two independent classifications agreeing is evidence;
one signal renamed twice would not be.

## Eleven genuinely open keys

Absent from the binary and **not** tool-marked, so neither reading explains them:

| key | in files |
|---|---:|
| `mCascadePartition0_2` · `0_3` | 244 each |
| `mCascadePartition1_2` · `1_3` | 136 · 162 |
| `mCascadePartition2_2` · `2_3` | 132 · 150 |
| `mMapAmbientColorA` | 18 |
| `EnableAutoExposure` | 3 |
| `mWaterParallax` | 2 |
| `DofImageSensorHeight` · `mCascadeNumber` | 1 each |

**The `_2`/`_3` suffixes in 244 files are the strong lead**: a numbered family that widespread is
far more likely read through a constructed name or an array index than not read at all. **A
constructed name leaves no literal**, which is the standing reason absence is never proof.

`mMapAmbientColorA` is the opposite case, and it comes with a control:

```
mMapAmbientColorR   70 files   008FA750
mMapAmbientColorG   52 files   008FA768     <- consecutive, all three found
mMapAmbientColorB   46 files   008FA780
mMapAmbientColorA   18 files   -- no literal --
```

**The instrument demonstrably finds this family and does not find the alpha.** An absence claim with
a positive control, which the standard permits — and a real modder fact: the alpha is authored in
eighteen files and read by nothing.
