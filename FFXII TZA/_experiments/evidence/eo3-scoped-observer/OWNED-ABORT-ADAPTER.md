# ASTRA — bind the retained abort to the designated game lifetime

This is the next bounded operating prerequisite of the existing EO3 task after
48735c54b. Its consumer is the scoped live runner and independent stopped-observer
review. Actual FF12 allocation, primary caller, queue issuance and health remain
unobserved. There is no new runtime platform or game session.

Question: can the already controlled pending-event abort body be reused while
rejecting a different process lifetime, image or event before termination or
continuation? Competing explanations include relying on PID alone, checking the
filename but accepting a different installation, or servicing the wrong pending
event after a failed identity check.

The cheapest sufficient method for this connection is offline source reuse and
synthetic dispatch. The native program controls already establish the particular
termination/effect ordering on this host. Re-running them would not establish
ownership of a future FF12 process. That future identity must be observed during
the authorized setup and rechecked through the opened process handle.

`owned_game_abort.py` pins the exact native control source and extracts only its
identity-query function and nested abort body. The abort AST fingerprint is
preserved; no WinDLL, launcher, debugger attach, fixture allocation or native API
is invoked at import. The adapter first validates the supplied identity against
the designated installation and exact shipping image hash. It then checks the
invocation PID and reuses the existing handle-based PID/creation/image/hash query
before the original pending-event check, termination and bounded event drain.
This does not prove the prepared identity was collected from the intended game;
the launch/setup receipt and pre-attach guard remain runner obligations.

The reused native receipts contain two different subjects with PID38728: the
earlier reader and the later stopped-instruction read-failure subject. The earlier
reader records parent, image and successful normal exit, but **no creation-time
field**. The later subject records creation134344741007691989. Do not invent the
earlier timestamp. The stale-time regression supplies laterCreation-1 explicitly;
its FF12 image/hash identity is also supplied, not a live FF12 observation.

The controls verify the positive API order, reject a changed PID/creation/image/
hash and a foreign pending event before termination, reject an invalid prepared
identity, prevent continuation after failed termination, and reject an unexpected
exit code as terminal success. These are synthetic callbacks using the exact
retained abort body. Native game behavior or ABI validation is not newly claimed.

The first checker attempted the later control's filename/schema for the earlier
reader and failed before dispatch. Its source and repair note remain. Reading
the actual raw ownership record exposed the absent earlier creation field; the
corrected checker represents that limit rather than filling it with an inferred
value. No prior semantic claim depended on the incomplete checker.
