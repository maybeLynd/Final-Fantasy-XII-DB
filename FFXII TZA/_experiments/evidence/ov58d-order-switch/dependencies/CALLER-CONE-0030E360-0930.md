# Caller-cone audit of `0030E360` — the OV58D named reach

Companion to [`RESIDUE-BOUNDS-0930.md`](RESIDUE-BOUNDS-0930.md). That record named
`0030E360` (`BattleStats_ChangeStatusAndProcessSideEffects`) as the one data-dependent reach:
`rec + 0xBC + 4·id` at `0030E594` and `rec + 0x13C + 2·id` at `0030E5AF`, with `id` the
unbounded `r8b` byte arg (`movzx edx, byte [rsp+0x40]` at `0030E588` / `0030E5A7` — the byte
is used verbatim, never masked). Region A (`state +0x4748..+0x4F10`, the field immediately
after the 40-record array which ends at `state+0x4748`) is reached iff the record index `k`
is `38`/`39` (dword: `id ≥ 0xB5`/`id ≥ 0x43`; word: `k=39`, `id ≥ 0x46`) or `k ≥ 40`.

This note asks the follow-up the residue record deferred: **do any callers actually pass an
out-of-contract `id`?** Verdict: **yes — two sites.** The assumed `id ≤ 0x1F` caller contract
is falsified by `002FDDA0`.

## The two out-of-contract sites in detail

`002FDDA0` is a message switch on `dx = word[unit+0x714]` (`cmp r8d,0x4158; ja` reject, jump
table at `0x2FE534` covering `0x4046..0x4091`, read directly from the binary). Two single-value
arms call `0030E360` with `rcx = qword[unit+0x698]` (the unit's stats-record pointer):

- `dx=0x4049` → arm `002FDF18` → `r8d = 0x4049 − 0x51 = 0x3FF8` → **`r8b = 0xF8`**
- `dx=0x404A` → arm `002FDF5A` → `r8d = 0x404A − 0x71 = 0x3FD9` → **`r8b = 0xD9`**

Both byte-truncate to values far above the 32-slot container contract. Effect on the record
for stats-record index `k` (`rec = state + 8 + k·0x1C8`):

| `id` | dword site `rec+0xBC+4·id` | word site `rec+0x13C+2·id` |
|---|---|---|
| `0xF8` | `rec+0x49C` — `k=38`: `state+0x4854` (region A); `k=39`: `state+0x4A1C` (region A); `k≤37`: inside rec `k+2`/`k+3` | `rec+0x32C` — `k=39`: `state+0x48AC` (region A); `k=38`: `state+0x46E4` (inside rec 39); `k≤37`: inside rec `k+2` |
| `0xD9` | `rec+0x420` — `k=38`: `state+0x47D8` (region A); `k=39`: `state+0x49A0` (region A); `k≤37`: rec `k+2`/`k+3` | `rec+0x2EE` — `k=39`: `state+0x486E` (region A); `k≤38`: cross-record, below region A |

So for **any** `k` these two arms write outside their own record, and for `k ∈ {38,39}` they
write into region A.

## What is still open — tightened 2026-09-30 (SWE2-STRUCT, second pass)

The `unit+0x698` assignment site is `0023A570` (`BattleUnit_ApplyUnitDefinition`) at
`0023ABFA`: `mov [unit+0x698], r15` where `r15 = qword[02EBF190] + 8 + 0x1C8·r12`
(`0023AAAA`–`0023AAC1`) — the state-record base plus `0x1C8` times the record index,
with **no bound check on `r12`**. `r12 = byte[spawn_row+0x23]` (`0023A8F3`), gated only by
`00322C50(ecx=2, edx=r12, r8=1)` at `0023AA59`, whose kind-2 arm (`00322C9A`) compares
against the runtime row count `[[02EBF130]+4]`.

`02EBF130` is documented (`authored-data-table-registry.md`, CB-11) as `battle_pack.bin`'s
party-definition table: **40 rows** — rows 0–16 characters/guests, 17–25 unnamed, 26 the
Chocobo, **27–39 the thirteen Espers**. So the record index is the party-definition row and
**records 38/39 are real slots — the last two Espers**. The residual therefore tightens from
"does any unit own rec 38/39" to: **does the message switch `002FDDA0` ever run on a unit
whose party-def row is 38/39 (an Esper) with `word[unit+0x714] = 0x4049`/`0x404A`** —
Espers are summonable combat units, so the slot ownership is not exotic; the open half is
whether those two message ids are ever delivered to such a unit (`002FDDA0`'s caller —
the indirect order-handler table `0x01EEC460` via `00305080` — is resolved in the third
pass below).

Separately, the unclamped `imul rcx, r12, 0x1C8` means a hypothetical `r12 ≥ 40` would store
an out-of-array record pointer into `unit+0x698` outright — only the bank row count stops it.

## The indirect edge is now identified — 2026-09-30 (SWE2-STRUCT, third pass)

`002FDDA0` has no `edges.tsv` callers because it is reached through a `.data` handler table,
not a direct call. The pump chain is fully static:

- `00233F70` (`BattleUnit_UpdateCombatFrame` outer) → `00308610`
  (`BattleUnit_UpdateCombatFrame`), the per-unit combat tick. Before the dispatch it checks
  only `[unit+0x708] != 0` (`0030868B`), a `word[unit+0x714]` liveness compare
  (`00308718`), `byte[unit+0x6B4]` state (`00308721`), and `word[[unit+0x708]+4] ≥ 0`
  (`00308736`) — **no unit-class or record-index filter**.
- `00308610` → `00307BE0` (`BattleUnit_AdvanceExtendedActionState`), which for
  `word[unit+0x714] > 0x21E` calls `00305080` (`00307C20`).
- `00305080` is the order dispatcher: `eax = msgid − 0x4000` (`003050D3`), bound
  `≤ 0x166` (`003050D8`), then `rdx = qword[0x01EEC460 + rax*8]` (`003050E1`–`003050E8`)
  and `jmp rdx` with `rcx = unit` (`003050FE`) — a tail-call to the per-message handler.
- The handler table `0x01EEC460` (358 entries, msgid `0x4000..0x4165`): **`msgid 0x4049`
  → index `0x49` → `@01EEC6A8 = 002FDDA0`**, **`0x404A` → `0x4A` → `@01EEC6B0 = 002FDDA0`**.
  Verified byte-wise against the shipping image. `002FDDA0`, `002FDA60`, `002FE910` share
  the `handler(unit*)` signature (each reads `word[rcx+0x714]`, `[rcx+0x708]`,
  `[rcx+0x6B4]`, returns `eax=1`).

So the chain `unit tick → 00305080 → table[0x49/0x4A] → 002FDDA0 → 0030E360(id=0xF8/0xD9)`
is complete static code. The dispatch applies to **every** unit with a live `+0x708` order
subobject — Espers included. What remains genuinely open is sender-side only: whether any
producer ever enqueues `0x4049`/`0x404A` (via `0030F760`, `BattleUnit_DispatchMessage`,
which writes `word[unit+0x714]`) on an Esper-slotted unit. A scan of `.text` immediates and
of the `.data` message-record region finds no static `0x4049`/`0x404A` producer — the ids
are most plausibly generated from script/ordered-action data, so this is a runtime
observation question.

## Status update to the residue record

`0030E360` is no longer "a reach excluded by the caller contract" — the contract is already
violated twice. The accurate summary is: **two call sites pass `id = 0xF8`/`0xD9`, escaping
the record for every `k`; region-A overlap needs the unit's record index ≥ 38, and record
38/39 = the last two Esper rows of the 40-row party table.** The remaining question is
whether an Esper-class unit can receive messages `0x4049`/`0x404A`.
