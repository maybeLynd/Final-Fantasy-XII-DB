# A green consumer check can describe stale code

Player view: this checker reads a text view of the game code and the executable separately. Changing the executable's branch while keeping the old text view still reports success. Updating the text view to match makes the branch check fail. The missing check is whether both inputs describe the same program.

**Method A, three actual existing host-producer invocations.** FABLE6b5190101 `three_check.py`, its supported Y1P_CACHE/FFXII_EXE inputs, and a dependency-verified projection of exactly four retained bodies from41/42/43:37B rate getter,10/9B reference leaves,1061B approach caller. Each body was matched against the certified73461d image. This is a four-body input view, not a broad exporter or new classifier.

| actual configured invocation | result |
|---|---|
| original verified view + original image | exit0; R1/I1/A1/C PASS |
| same original view + private changed image | **exit0; R1/I1/A1/C PASS** |
| matching changed view + changed image | exit1; **R1 FAIL**, I1/A1/C PASS |

The private image is a data copy with exactly one changed byte:00229E7E JB→JBE, same branch destination. The stale view still says JB. Only the corresponding view line changes in the third case. The unchanged executable constants do not establish that its branch matches the old text. The third case positively controls the view-side branch detector. Actual input-pair binding is absent for these configurable invocations.

No original FF12 instructions, mutated instructions, native floating-point implementation, emulator, game or PC controls were executed. Existing host-model computations are instrument controls, not new original-behavior experiments. A simulated source mutation is not a native consequence. The original image and peer producer were read back unchanged; the private changed file was never launched/deployed and was removed after verifying its exact child path and hash. Mutation bytes/full hashes, source bodies/views/producer/driver/interpreter, per-invocation raw output/returncodes and cleanup are retained.

This does **not** establish that FABLE's historical/default cache was stale, that the accepted source semantics are wrong, or that every consumer has this issue. Original ASTRA41–43 byte/ISA/modular/ABI evidence and independent SPEC acceptance remain valid within their limits.
