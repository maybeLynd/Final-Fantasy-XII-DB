# GF-4 caller observation: qualification before live exposure

Exact unresolved claim: which initialized caller invokes a concrete Phyre
post-effect render entry in a named game state, and does that caller walk a pass
list? Major system S-40 / Phyre post-processing. Consumer FABLE owns GF-4 and its
semantic page; OPUS owns any resulting ABI/caller relation. The broad phrase
"per frame" is a separate scheduling claim and is not answered by one hit.

H1: the observed caller selects the effect through a pass-list traversal.
H2: it invokes this effect by another route, independent of the pass query.
H3: no qualified invocation is observed in the chosen state. H3 is a bounded
negative, not global absence or a proof that the subsystem is inactive.

Chosen method: A for exact shipping entries and retained instrument controls;
C is necessary for the actual caller/initialized object/state. B can execute
an invented caller but cannot identify the game's real scheduler. Do not run
all three or repeat the already published static caller sweeps.

## Evidence already sufficient, and missing preparation

36 exact original tables at D61E50 + i*50 contain ten render targets at slot 6
(offset 30); slot 5 (offset 28) is the pass query. Each target is qualified as
an exact PE RuntimeFunction entry, with full raw bytes and first instruction.
This establishes static identity only. Resolve each preferred-image address
through the actual module load base; verify corresponding mapped bytes before
arming. Reject an interior/prologue instruction or slot-5 address substitution.

EXP-039 actually collected 41 complete 64-byte stopped stack reads and a known
native return address, with a cold control and cleanup/heartbeat receipts. It
qualifies that read in its own disposable program. Its final target exits 1
because the historical harness explicitly terminates it; do not relabel that
as a natural exit 0 or FF12 health. The EXP-038 capture it used still contains
the demonstrated foreign-step dispatch defect and has a duration-only budget.
The independently accepted EXP-127 candidate fixes dispatch in its tested path,
but does NOT record stack bytes and also has a duration-only main loop. Neither
unchanged CLI is a ready, first-hit-bounded GF-4 instrument. Their qualifications
do not combine automatically. No replacement/deployment is made by this packet.

The exact save/scene/preset that instantiates a chosen effect is not supplied by
the original request. FABLE/FRONTIER must name that state, activation trigger,
actual target class and consumer acceptance before expensive live setup. A
generic title/Stepping launch is not proof that this subsystem is initialized.
Existing verified input/save recipes should be reused once the state is chosen.
S19's exhausted input setup allowance remains separate and is not reset here.

## Smallest future discriminator, subject to preparation

1. Pin EXE, mapped module/code, observer and reader identity; verify fresh
   disposable save/config copies, original hashes and cloud protection. Reserve
   @runtime and ensure no user stop/takeover. Prove initial presentation and
   ordinary registered input/accepted menu response independently of attach.
2. Reuse the stopped stack reader with the ownership-qualified dispatch decision
   only after their scoped composition is qualified on the existing disposable
   known-return target. Require an owned positive, foreign-event delivery
   negative, complete stack read/order, first-hit stop, cleanup and response.
   Do not rebuild the laboratory or call a Python fixture native qualification.
3. Limit the first game exposure to ONE selected render entry and at most ONE
   recognized target event, with a one-second armed deadline and a separate
   three-second cleanup deadline. Budget expiry or foreign/unreadable event
   stops semantic acceptance. No four-hot-breakpoint window or unchanged retry.
   Counts are upper bounds, not targets. Confirm this scope with the consumer.
4. At the recognized stopped entry, before prologue/resume: preserve exception
   ownership, thread, RIP/RSP and registers; obtain exactly 64 stack bytes;
   read the receiver's vtable and verify slot 6 against the selected entry and
   known table. Bound the additional reads to this identity and one return
   location. Failed/null/short/out-of-module reads invalidate identification.
   A hit at the base entry does not identify a specific derived effect without
   the receiver/vtable proof. Do not dereference opaque arguments speculatively.
5. Preserve top-qword module/address and the corresponding original caller code.
   A pointer into text is not enough: decode from a qualified instruction
   boundary and verify the call ending at that address plus receiver/target
   dataflow. Tail calls may expose an earlier caller; narrow accordingly.
   RDX is opaque until the SLOT-6 ABI is established: slot-5's second argument
   being a pass record cannot be transferred to slot 6 by shared slot names.
   Only after an actual caller is identified should offline code/list analysis
   decide the pass-list hypothesis or name a missing discriminating read.
6. Clear/read back debug state at a stopped event, detach/close scoped handles,
   and verify ordinary input registration, accepted menu open/close and visible
   responsiveness, not just CPU samples. Observe a bounded 65-second post window
   for fatal dialogs/health, then normal game exit. This is a defined health
   window, not proof against arbitrary delayed failure. A fatal dialog, failed
   response/cleanup or save integrity invalidates semantic acceptance.
7. Compare all backed-up saves/config and original binary hashes; preserve and
   restore changed disposable settings as necessary, verify target/helper exit,
   release @runtime and reset PC control as soon as UI work is finished.

## Acceptance, limits and consumer package

A valid first-hit packet may name a caller/receiver relationship in that specific
state, with raw stack/register/memory/API/state/health evidence, exact provenance,
reducer and restoration receipts. It does not establish frame cadence, all
classes, all scenes, lifetime/reuse or native draw effects. If the caller proof
succeeds but pass-list discrimination does not, preserve the useful relationship
and leave traversal open. A zero-hit arm requires a qualified observer/target
state and remains bounded. A failed session remains INVALID even with raw hits.

The known native x87 metadata counterexample remains a disclosure, not a claimed
FF12 crash cause or a complete transparency fix. Do not chase that host mechanism
unless the selected observation depends on it. No live trace is launched or
prepared state falsely certified by this preflight. Canonical GF-4 remains OPEN.
