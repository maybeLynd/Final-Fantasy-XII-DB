## 1. Interface

The system has two halves that never call each other:

- **Action selection.** A per-frame driver and a pending-selection queue call one selector. The selector tries four
  order sets in a fixed order. Each attempt is the **gambit walk**: try a subgroup's records in order, evaluate each
  one's condition and target, and commit the first that matches.
- **Enmity.** A per-foe threat vector. Landed actions raise it, propagation spreads it and redistribution moves it.
  A periodic decay drains it, and the selector's condition language reads it.

The configuration layer (three gambit banks per party member, rebuilt into runtime order sets) feeds the first half.

## 3. Contradictions (statements a re-implementer would have to choose between)

### 3.1 Value-changing (counts, offsets, addresses, constants, formulas) — page-text only - needs local check

**C-V1. Highest-vs-lowest seed: the pseudocode and the prose say opposite things.**
- Side A: `gambit-evaluation-and-enmity.md:650-651`: "`seekMin  = ~opcode & 1;` / `best     = seekMin ? 0x7FFFFFFF : 0x80000001;`".
  The same formula is repeated at `:675-676`. Read literally, an **odd** opcode gives `seekMin = 0`, which seeds
  `0x80000001` and keeps the larger value (highest).
- Side B: `gambit-evaluation-and-enmity.md:679-681`: "An **odd** opcode seeds `best` to `INT_MAX`, so every comparison
  keeps the smaller value - **lowest**. An **even** opcode seeds `0x80000001`, so every comparison keeps the larger -
  **highest**."
- Also on side B: the Z-1 table (`:697`: "`r12 = (~opcode) & 1`, so an **even** opcode is the "true / highest / ≥"
  reading") and its rows (`:707`: "**2 / 3** … **highest / lowest**"; "3-4 "lowest HP"").
- Status: no dated correction strikes either line, so there is **no favoured side**. The 2026-09-12 Z-1 table agrees
  with side B, but it does not amend the seed lines.
- Page-text only - needs local check. The direction of every best-of opcode depends on it.
